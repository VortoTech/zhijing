# 知镜决策陪伴 Agent

## 是否适合

适合，但核心应是“帮助用户形成判断”，不是生成一个更像答案的答案。知镜已经有双方理由、分叉条件、原话、评论异议和来源核对，这些正好可以成为 agent 的证据层。agent 负责追问、整理、关联和暴露缺口；原话层继续负责约束它。

一句话定位：**知镜助手陪用户把问题问清楚，把与其情况相关的真人经验放到前面，并说明建议依赖哪些前提。**

## 推荐流程

1. **明确问题**：确认比较的 A、B 和用户真正想解决的决定。
2. **收集条件**：优先用当前材料里已有的分叉提问，允许“不确定”和跳过。
3. **整理脉络**：将理由按共同议题排列，区分事实、经验、价值偏好和假设。
4. **证据对照**：每个解释都带原话、作者、异议和适用前提；缺证据时明确说缺什么。
5. **个性化建议**：输出“优先核对什么、当前更需要避免什么、下一步补什么信息”，而不是宣布唯一选择。
6. **回看与修正**：用户可以标记“不适合我”“这个条件更重要”或补充新情况，agent 据此调整阅读顺序并记录变化原因。

## Agent 的输出契约

每次回复应包含以下信息中的必要部分：

- `understanding`：对用户问题和当前处境的复述。
- `relevant_evidence`：与用户条件直接相关的引用 ID，不复制或改写引用。
- `assumptions`：本次建议依赖的前提。
- `counterpoints`：同一来源评论区的反驳或补充条件。
- `gaps`：现有材料无法回答的问题。
- `next_question`：一个最能减少不确定性的追问。
- `advice`：可撤回的行动建议，明确它来自哪些用户条件和证据。

生成后的服务端校验：引用 ID 必须存在；原话必须从记录按 ID 取出；不得生成新的“用户事实”；没有证据的判断必须标为推测；回复不得把条件计数转换成胜率。

## 登录画像怎么用

登录后浏览器只获得昵称、签名和头像；服务端可在授权有效期内读取近期收藏与本人内容（收藏体检、答主视角、收藏推测）。OAuth token 仅在服务端内存保存。长期画像见下方「实现状态」：只在用户同意后保存，也不把收藏主题直接视为用户的人生目标或价值观。

画像建议分三层：

| 层级 | 内容 | 使用规则 |
| --- | --- | --- |
| 用户明确填写 | 当前阶段、预算/经济压力、城市限制、时间窗口、风险偏好、不可接受项 | 可直接用于当次建议；展示并允许修改、删除 |
| 用户明确选择 | 哪个条件更重要、哪些原话与自己相关/不相关 | 用于排序和追问；保留来源与时间 |
| 从授权内容推测 | 收藏主题、近期关注方向、重复出现的问题 | 只能作为待确认线索；先问“这是否代表你最近在考虑……” |

数据模型至少保留 `value`、`source`（declared/selected/inferred）、`evidenceRef`、`confirmedAt`、`expiresAt`。跨会话保存前要单独征得同意，并提供“查看我的画像、修正、删除、关闭个性化”。敏感信息不要从收藏中自动提取或长期保存。

## 实现状态（2026-09-14）

原方案由 Codex 起草，三个阶段一起落地，按比赛节奏收窄了范围：

| 方案 | 实现 | 位置 |
|---|---|---|
| 证据导览（选条件） | 条件用独立按钮选择、可撤销；选择只作为决策陪伴的输入，不重排、不计票；两边原话始终并排，选中的一边标出 | `public/app.js`、`public/advisor.js` |
| 会话式厘清 `/api/advice` | 输出契约同上（understanding / points / counterpoints / assumptions / gaps / advice / next_question / fact_proposals）；原话用 `e*` 编号、读者反驳用 `p*` 编号，服务端按编号取原文；无编号的判断标「推测」；建议只能依据用户确认过的情况；出现胜率、百分比、「你应该选」或「选/去 + 选项名」时驳回并让模型重写一次 | `src/agent.mjs` |
| 找同路人 `/api/peers` | 用用户确认过的情况（最多 3 条）按「情况 + 两个选项 + 经历」去知乎搜，只留带自述的回答，再加原来那批回答下带自述的评论；模型只挑编号，「自述处境」必须是说话人在讲自己（程序把关，「我觉得 / 我建议」不算），「经历与选择」必须出自同一说话人；「倾向」只有原话里提到这一边、没提另一边才显示；模型一个没挑时再提醒一次；没找到的结果不缓存 | `src/peers.mjs` |
| 材料不够时补充检索 | 模型给出搜索词时最多再搜知乎一次，搜到的原话同样按编号挑选；和实时检索共用每日次数 | `src/agent.mjs` `followUpSearch` |
| 登录画像三层 | declared：用户自己填或在对话里点「记下」（必须是用户原话里的一段）；selected：条件选择（按问题保存在决策记录）；inferred：从近期收藏推测，确认前 `pending`、不进建议 | `src/store.mjs`、`/api/profile*` |
| 长期保存 | PostgreSQL；默认不存「你的情况」，用户打开「记住我的情况」才写库；关闭即删除；可一键删除全部数据；情况 180 天、推测 7 天过期；OAuth token 不入库 | `docs/deploy.md` |
| 前提与来源 | 对照整理新增 `premise`：答主在同一回答里交代的适用前提，按编号取出挂在原话下；示例「薪资体现当下价值」已补 | `src/pipeline/compare.mjs` |

没有做的：「与我有关 / 不适用」逐条标注、跨问题的画像摘要、用户可见的完整对话历史（只保存每个问题的最近选择与建议）。

## 验收重点

- 同一问题下，补充条件后能解释内容为何调整。
- agent 的每个核心判断都能追到引用或被明确标成待确认假设。
- 用户可以跳过问题、撤销选择、纠正画像，并看到纠正立即生效。
- 切换问题、退出登录和授权过期时不会沿用错误的用户条件或旧建议。
- 收藏推测未确认前不会进入建议事实层。
- 评估不仅看用户是否点击，还要看用户能否复述主要分歧、识别关键前提，并说出下一步需要核实的信息。
