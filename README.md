# 知镜

把一条按赞数排序的搜索结果，变成一张有结构的阅读地图。

它不判断谁对。它只做一件事：把读者已经说出口的反驳，摆到那条答案的同一屏上，并逐字引用、指向原文。

## 跑起来

```bash
node --version      # 需要 >= 22
npm run build:snapshot   # 从探针数据重建离线样本（已提交，通常不用重跑）
npm start                # http://127.0.0.1:4318
```

零依赖。没有 `node_modules`，没有构建步骤。离线样本已随仓库提交，所以**不需要任何凭据**就能跑通全流程。

```bash
npm test    # 含处境、数据一致性、来源与缓存的回归测试
npm run check   # 语法检查
```

### 判断一个新话题值不值得做

```bash
npm run analyze -- data/raw/r-job.json first-job
```

不需要模型、不需要凭据。它数出这个话题**最多**可能有多少条实质异议，用来在花钱跑模型之前先筛掉撑不起来的题材。详见下面「适用边界」。

## 当前阅读体验（2026-09-12）

- 默认展示标题相关的 5 条异议/前提记录，展开第一条。原句高亮，长上下文按需展开；36 条标题相关回答与全部 60 条样本均可切换。标题词筛选可能漏选，不宣称语义相关性已验证。
- 不再把机械首句叫作“核心主张”。有异议时展示被回应的原句，其余展示标注清楚的原文片段。
- 每张卡片同时列出原站评论数和本次取到的评论数；取到 0 条显示“评论数据不足”。
- 个人条件只用于查找已标注为补充条件的评论原话，不判定整条建议是否适用。支持话题包中的 terms 别名；多条件分别显示覆盖，零命中明确提示。否定与主体由完整原话供读者核对，不再生成“与你的处境相符”标签。
- “考研还是工作”没有离线样本，入口显示准备中并禁用；信息型话题也不可选。实时未配置时禁用实时入口。
- 切换话题/模式会取消旧请求、清除旧结果；加载、失败和取消有反馈与恢复按钮。排序、条件和显示范围在当前结果上本地计算，不发起新的模型调用。
- 服务端按话题/模式合并在途分析并缓存 15 分钟，每个服务实例独立缓存；失败不缓存。数据说明保留人工/模型归类来源与时间，内部诊断位于页面底部折叠区。
- 测试缓存使用注入的假上游，不代表实时知乎与模型联调已完成。

## 引用与判断边界

### 实时可靠性补齐（2026-09-12）

- 模型漏回、批次失败或引用校验未完成的记录保留原文，单独显示“分析未完成”，不计为“未见异议”；部分结果可重试，统计不再静默缩小分母。
- 评论过滤只排除完整的短赞同语，不按“说得好”“同意”等前缀删除后续反驳。
- 模型最多两批并发，每批最多 6 条并按输入字符预算拆分；截断或遗漏最多重试一次。多路检索允许部分成功，缺口明确显示，部分结果不写入成功缓存。
- 第一份工作仅为内部试用候选，除实时凭据外还须 `ZHIJING_ENABLE_PILOT=1`；未验证考研话题保持关闭。试用开关不代替公网鉴权。
- `npm run smoke` 检查离线链路；`npm run smoke -- --live` 显式调用真实上游并可能产生费用。
- `npm run evaluate -- gold.json predictions.json` 对独立人工金标准计算精确率、召回率和完成率；本轮尚未取得真实模型评估成绩。

完整流程、评估格式和待验收条件见 [实时 MVP 验收](docs/acceptance.md)。

**一、不做判断，只做转述。**
系统不评价哪条答案对，也不评价哪条异议成立。它把反对意见摆到同一屏，并给出回原文的链接。判断权在读者。

**二、任何展示出来的异议，必须能在原文里逐字找到。**
`verifyClassification` 会检查：

- 评论下标必须真实存在于该记录的评论列表里；
- 异议引用的评论原文必须逐字一致，不做改写；
- `targetClaim` 必须是答案原文的连续子串；
- 非 framing 类异议（`off_topic` / `self_contradiction` / `counter_example` / `questions_data`）必须指向原文中的某一句，指不出来就丢弃；
- 模型标记为「实质」但内容只是附和的，仍然丢弃（`宁可漏判，不可错判`）。

校验保证引用文字来自所取到的原文，不能证明评论与目标句在语义上构成反驳，更不能证明评论内容正确。实时分类仍需语义评估。离线异议由人工标注；构建也会校验引文来源。

## 三态

| 状态 | 含义 |
|---|---|
| 有读者提出异议 | 评论区有人针对这条答案提出实质反驳 |
| 有前提条件 | 有人补上了这条建议成立所需的适用条件 |
| 未见实质异议 | **这不等于这条回答被验证过。** 只表示本次取到的精选评论里没有出现实质异议 |

第三态是刻意这么写的。一个沉默的标记很容易被读成「可信」——那是这套机制最容易骗到自己的地方。

## 诊断

每次请求都会算一遍：这个话题的数据到底撑不撑得起三态标记。

它同时在几个「面」上算标记密度，并给出一个判定：

- `viable` — 整张列表就撑得住
- `scoped` — 整张列表不行，收窄到有评论的那层才行
- `marginal` — 压在门槛线上，换个门槛结论就反
- `too_sparse` — 信号太稀，建议换话题

它还会按赞数从高到低、每五条扫描一次，描述本次样本最深达标位置；这不能推定产品的最大覆盖范围。

门槛（15%）是人为约定，不是定律。真实数据跑出来是 8.3% / 14.7%——所以这里给的是区间判断，不是「是 / 否」。

当前离线样本的实测结果见 `my-knowledge/docs/projects/zhihu-hackathon-三态标记实测-2026-09.md`。

## 适用边界

**只适用于观点 / 经验型问题。**

信息 / 政策型问题（落户、报税）的精选评论覆盖只有约 14%——大多数条目根本没有评论。这不是缺点，是这类问题的常态：答案对错由政策文件决定，不由读者争论决定。`topics/luohu-tax.json` 作为反面样本保留，服务端遇到它会直接返回 422，而不是硬跑出空结果。

这条边界是用**独立样本**验证过的，不是推断：

| | 观点型（第一份工作） | 信息型（落户/个税） |
|---|---|---|
| 有精选评论的条目 | 34/60 = **56.7%** | 9/60 = **15.0%** |
| 评论总数 | 86 | 16 |
| 过机械实质过滤的评论 | 86.0% | 87.5% |
| 标记密度上界 | 53.3% | **11.7%** |

两个关键读法：

1. **差距来自数量，不是质量。** 两类的评论「干净程度」几乎一样（86.0% vs 87.5%）。信息型不是评论更水，是根本没有评论。这正好印证了机制解释：答案对错由政策文件决定，读者没什么可争的。
2. **11.7% 的上界低于 15% 门槛，所以拒绝是算术，不是保守。** 即使模型把每条候选都判对，也到不了门槛。信息型话题不必配置凭据。

反过来，观点型的上界 53.3% 远高于门槛，但人工标注后的真实密度只有 8.3%——**上界只能用来排除，不能用来放行**。机械过滤太宽松，话题是否可用必须靠真实分类。

（两类话题声明的覆盖率 0.52 / 0.14 与实测差 4.7 / 1.0 个百分点，均已复核一致。）

## 两边对比（2026-09-13）

用户反馈先是「结果没有实质帮助」（零散的评论异议回答不了「我该怎么选」），改成条件清单后又觉得「割裂」：没有把两个选项放在一起比，清单和下面的评论异议互不相干。现在结果页是一张围绕这个选择的对比图：

- **两边各自的理由**：左右并排，「选国企的人说 / 选私企的人说」，每条理由附原话。
- **决定你选哪边**：3–5 个分叉条件，每个恰好两条分支（例如「低回报专业 → 国企 ｜ 高回报专业 → 私企」），两条分支倾向不同选项，各自都有原话；同一句原话不能同时支持两边，找不到另一边原话的条件不展示。
- **引文不可能被改写**：程序先把赞数靠前的 24 条相关回答切句编号、评论逐条编号，模型只挑编号，页面按编号取原文（`src/pipeline/compare.mjs`）。原型对比：让模型抄原话时国企/私企一题 15 段丢了 13 段；改成挑编号后 0 丢弃、耗时从 13 秒降到 5–6 秒。标题和分支说明仍是模型归纳，页面标明。
- 与异议归类并行，不增加等待；失败重试一次，仍失败显示「没能整理出对比」并可重新整理，只短时缓存。问题不是二选一时提示换成「A 还是 B」的问法。
- 离线示例的对比图由 `npm run build:comparison -- first-job` 预先生成到 `data/compare-first-job.json`，测试逐条核对原话。
- 原来的逐条异议作为「原始回答与评论区」放在最后，是对比图引文的出处。

## 自由提问（2026-09-13）

首页改成一个搜索框加 6 个示例问题。「第一份工作选高薪还是成长」直接打开整理好的示例；其余问题走实时检索（`POST /api/ask {question}`）：

1. 模型把问题规划成 6 路检索词、标题关键词，并判断是不是查资料类问题（政策、流程、数据）。查资料类直接返回 422 和换问题的提示，不花检索额度。规划失败时只用原问题检索。
2. 标题命中关键词的有评论回答少于 6 条时，不按标题筛选，全部送去分析。
3. 之后照常检索 → 归类 → 逐字校验。与话题接口共用 15 分钟缓存、部分结果 3 分钟缓存和每日次数上限。
4. 链接带 `?q=问题` 可以直接分享一次提问。日志不记录问题原文。

需要实时凭据且 `ZHIJING_ENABLE_PILOT=1`，否则首页只能看示例。

## 精确率补强（2026-09-13）

- **只分析标题相关的回答**：标题不含话题 `focusTerms` 的回答不送模型，标为「未分析（与话题不相关）」，不计入标记密度，也不显示成「未见实质异议」。
- **二次复核**：第一遍找到的候选异议再逐条复核一次，只删不增。复核判否的丢弃；复核失败或漏回的候选一律不展示，并把该条标为「分析未完成」。
- **提示词加反例**：顺着回答补强、复述赞同、离题抬杠、单纯提问都不算异议。
- **投票**：第一遍默认跑 2 次取并集（防漏判），复核每条候选投 3 票、过半才保留（防误判）；复核时「补充适用条件」要区分条件和理由。次数可通过 `classify()` 的 `passes`、`reviewVotes` 参数调整。实测效果与取舍见 `audit/model-eval-2026-09-13.md`。
- 思考型模型必须经 `AI_EXTRA_BODY` 关闭思考，否则单次请求会超过 25 秒上限。
- **检索限流**：知乎检索有频率限制，8 路并发只成功 2 路（`Code 30001 rate limit exceeded`）。现改为逐路间隔 700ms 发送、限流时重试一次；实测 8 路全部成功，冷启动约 16 秒。
- 以上改动在开发样本上调过，评估数字偏乐观；独立金标准评估仍未完成。

## 配置（仅实时模式需要）

```
ZHIHU_ACCESS_SECRET=   知乎开放平台凭据
AI_BASE_URL=           模型地址（HTTPS，本机地址除外）
AI_API_KEY=
AI_MODEL=
AI_EXTRA_BODY=         可选，并入请求体的 JSON 对象，例如关闭思考 {"thinking":{"type":"disabled"}}
ZHIJING_LIVE_DAILY_LIMIT=200   每天最多触发多少次真正的实时检索+模型分析（缓存命中不计），超出返回 429
PORT=4318
HOST=127.0.0.1
```

没配齐时 `/api/config` 会如实报告 `liveReady: false`，界面提示改用精选样本。**系统不会在实时检索失败时偷偷替换成样本数据**——那会让演示很好看，也会让结论完全不可信。
